= Roadmap — crystal-combine-pdf
:toc: left
:toclevels: 2

État au 2026-05-03 : v1.0.31.23 publiée. Couverture API stable
(`merge`, `number`, `assemble`, `compress`), build déclaratif via
`.crystal-combine-pdf.yml`, 5 profils à l'`init`, config user
globale, compression profonde via `aloli-crystal/ghostscript`.
89 specs verts, ameba clean.

Cette roadmap décrit les chantiers identifiés pour les itérations
suivantes — ordre indicatif, à arbitrer au fil des retours
utilisateurs.

== Court terme — évolutions du shard

[cols="3,1,1,5"]
|===
| Item | Sév. | Effort | Description

| **Déduplication des ressources au `merge`**
| 🟢
| M
| Aujourd'hui, fusionner N PDFs qui partagent la même police
  l'embarque N fois. Identifier les objets dupliqués (hash du
  contenu sérialisé) et fusionner avant l'écriture. Bénéfice
  taille de l'ordre de 10-30 % sur des livrets typiques.

| **`insert(location, data)` / `remove(page_index)`**
| 🟢
| S chacun
| Édition fine d'un PDF existant : ajouter une page de garde, un

| **Lecture de PDF chiffrés** (RC4 v1/v2, AES-128, AES-256)

| 🟡

| 🟡
| M
| `start_at`, `font_name`, encadré coloré, `opacity`, numérotation

== Long terme — applications dérivées

Deux chantiers stratégiques décidés le 2026-05-03 : porter
combine-pdf au-delà du public Crystal/CLI pour atteindre le grand
public, **et servir de vitrine technologique de la société ALOLI**
(démonstrateur public de la qualité de production de l'écosystème
Aloli — pas un projet jouet).

=== A — Application web gratuite (vitrine ALOLI)

🔵 — initiative stratégique. **Lancement prévu mi-mai 2026.**
Effort estimé : **L à XL** (1-2 sem. selon polish).

==== Identité retenue

* **Nom : alolipdf** (gratuit) + **alolipdf Pro** (payant).
* **Domaine : `alolipdf.app`** *(TLD `.app` opéré par Google, HTTPS
  forcé via préchargement HSTS — cohérent avec la nature
  application web et avec une cible internationale).*
* **Multilingue dès la v1** — c'est un argument de la décision : le
  service vise une audience au-delà du francophone, le `.app` neutre
  est plus adapté qu'un `.fr`.
* **Double rôle** : utilisation en ligne **+** page de
  téléchargement de l'application desktop (chantier B). Une seule
  marque, une seule URL, deux modes (online/offline) qui se renvoient
  l'un à l'autre.
* **Modèle freemium** : la version gratuite reste utile pour le
  livret occasionnel (jusqu'à 7 pages, filigrane visible) ; la
  version Pro libère les contraintes pour l'usage professionnel ou
  régulier. Cf. section « alolipdf vs alolipdf Pro ».

==== Cible

* Particuliers / associations qui n'ont pas envie d'installer
  Crystal ni Ghostscript ni de toucher à une CLI : livret de messe,
  livret de mariage, programme de concert, dossier scolaire combiné.
* Aussi un banc de test pour combine-pdf en conditions réelles avec
  des PDFs variés (Word, LibreOffice, scans, exports web).
* **Vitrine ALOLI** : démontrer la stack complète (Crystal + Marten
  + HTMX + Bulma + Opal + déploiement Aloli) sur une app utile, pas
  un exemple jouet. Sert de référence dans les démarches commerciales.

==== Stack envisagée

[cols="1,3"]
|===
| Layer | Tech

| Backend          | **Marten** (framework Crystal Aloli-friendly). Dépendance directe sur `crystal-combine-pdf` et `aloli-crystal/ghostscript`.
| Templates serveur | Templates Marten + HTMX pour les interactions I/O (upload, polling de job, téléchargement).
| Client-side rich  | **Opal** (Ruby → JS) pour drag-drop, validation immédiate des fichiers, thumbnails, détection auto de l'OS sur la page Download. `aloli-crystal/deploy --opal-assets` gère déjà la compilation.
| Styling          | **Bulma**. CSS framework pragmatique, pas de processus de build lourd, mode dark prêt.
| i18n             | Module Marten i18n natif. **FR + EN dès la v1**. Trajectoire d'extension formalisée — cf. section « Stratégie multilingue » ci-dessous.
| File upload      | Multipart standard, taille max ~50 Mo, stockage éphémère (`/tmp/<uuid>/`, purge **à T+10 min** via cron). Cf. note « Pas un service de transfert ».
| Queue            | Synchrone via `Process.run` tant que les jobs restent < 30 s ; passer à un worker dédié si la latence devient un problème.
| Auth             | Aucune en v1 (anonyme, lien éphémère pour télécharger). Identité Aloli optionnelle plus tard via `aloli-crystal/saml` ou `aloli-crystal/kemal-auth`.
| Déploiement      | `aloli-crystal/deploy` sur serveur Aloli. Workflow déjà rodé pour Marten + Opal.
|===

==== HTMX vs Opal — répartition

Côté serveur (HTMX) : upload multipart, soumission du formulaire
(profil, options), polling du status, téléchargement, listing des
releases desktop (page Download), bascule de langue.

Côté client (Opal) : drag-drop visuel pour réordonner la liste de
PDFs, calcul live de la taille estimée de la sortie, thumbnails de
première page (PDF.js wrappé), détection auto-magique de l'OS du
visiteur sur `/download` pour proposer le bon installeur en haut.

==== Routes / pages prévues

* **`/`** — page d'accueil, démo intégrée (drag-drop PDFs).
* **`/app`** — application complète (upload, profil, deep, lien
  éphémère).
* **`/download`** — page de téléchargement de l'application desktop
  (chantier B). Détection auto OS pour mettre l'installeur adéquat
  en haut.
* **`/about`** — vitrine ALOLI : stack utilisée, autres shards de
  l'écosystème, contact pro.

==== Fonctionnalités v1

* Upload de N PDFs avec drag-drop pour réordonner (Opal).
* Choix du profil (`booklet` / `book` / `report` / `slides` / `minimal`).
* Toggle « compression profonde » (case → `--deep`).
* Lien de téléchargement éphémère (purge **à T+10 min**).
* Aperçu de la première page + nombre de pages estimé.
* Bascule de langue FR / EN visible dans l'en-tête.
* En-tête « Powered by Aloli » avec lien vers le site corp.
* Page `/download` avec installeurs desktop + détection OS.

==== Pas un service de transfert (anti-abus)

Décision Philippe (2026-05-03) : la durée du lien éphémère est
volontairement très courte — **10 minutes**. Ce n'est *pas* un
service à la `wetransfer` ni à la `transfer.sh`, et ALOLI n'a pas
vocation à servir de relais pour s'envoyer des PDFs entre tiers.

Conséquences concrètes sur la conception v1 :

* Aucune fonction « envoyer le lien par e-mail ».
* Aucune URL parlante / mémorisable du résultat (juste un UUID).
* `Cache-Control: private, no-store` + `X-Robots-Tag: noindex` sur
  la page de téléchargement (un lien partagé par accident ne
  pollue pas Google).
* Le job de purge tourne toutes les minutes (`/tmp/<uuid>/` plus
  vieux que 10 minutes → suppression immédiate).
* Limite raisonnable de fichiers concurrents par IP pour éviter le
  squatting de stockage.
* Si l'utilisateur rate sa fenêtre, il re-upload — friction
  intentionnelle, pas un bug.

==== Hors-périmètre v1

Comptes utilisateurs, historique persistant, OCR, édition
page-par-page (réordonner / supprimer / scinder), signatures, envoi
par e-mail du lien, partage social.

==== Pricing — propositions à arbitrer

Trois pistes, à choisir selon le ton commercial souhaité :

[cols="2,3,3"]
|===
| Modèle | Tarifs candidats | Pour qui

| **Abonnement mensuel / annuel**
| **4,99 €/mois** ou **49 €/an** *(2 mois offerts)*
| Usage régulier, ratio prix/valeur sain. Modèle dominant chez les concurrents (Smallpdf 9 €/mois, iLovePDF 4 €/mois). Génère du récurrent — bon pour le P&L.

| **Pass à durée limitée**
| **9,99 €** = 30 jours Pro
| Usage ponctuel intense (livret de mariage, dossier scolaire…). Sans engagement, achat impulsif. Bon complément à l'abonnement.

| **One-shot par fichier**
| **0,99 €** par PDF généré sans limite ni filigrane
| Achat très bas, pas de friction. Mais comptabilité plus lourde (Stripe metering).
|===

**Recommandation pour démarrer** : abonnement annuel **49 €/an**
+ pass mensuel **4,99 €/mois** (= deux faces de la même offre,
permet à l'utilisateur d'essayer 1 mois avant de s'engager). Le
one-shot peut venir plus tard si la traction le justifie.

Stack paiement candidate :
* **Stripe** — incontournable, cartes + SEPA, gestion abonnements
  native. Frais ~1,5 %+0,25 € par tx (CB UE).
* **Mollie** — alternative européenne, frais similaires, support
  Bancontact/iDEAL/Klarna utile pour les marchés DE/NL/BE/AT.

==== Stratégie multilingue

Décision Philippe (2026-05-03) : viser progressivement **toutes les
langues de l'UE** (24 langues officielles) puis évaluer une
extension hors UE.

Approche en 4 phases pour rester réaliste sans diluer la qualité.
Pourcentages = part de la population UE qui a la langue comme
langue maternelle (CE 2022). FR + EN couvrent déjà ~17 % + langue
seconde majoritaire pour 38 % supplémentaires.

[cols="1,2,3,4"]
|===
| Phase | Échéance | Langues ajoutées | Couverture EU cumulée

| 1
| **v1, mi-mai 2026**
| **FR + EN**
| ~16 % natif + EN comme L2 dominante

| 2
| v1.x (T+1 mois)
| Top 5 par population : **DE, IT, ES, PL, RO**
| ~85 % natif

| 3
| v2 (T+3 mois)
| Reste de l'Europe centrale et continentale : **NL, EL, PT, HU, CS, SV, BG, DA, FI, SK**
| ~98 % natif

| 4
| v2.x (T+6 mois)
| Petites langues UE : **HR, LT, SL, LV, ET, GA, MT**
| 100 % UE

| 5 *(à évaluer)*
| ouvert
| Hors UE : NO, IS, RU, UK, TR — selon traction & contributions
| —
|===

==== Processus de traduction

* **Source de vérité** : un fichier YAML par langue (par ex.
  `locales/fr.yml`, `locales/de.yml`...), géré via le module i18n
  Marten.
* **Premier jet** : DeepL (excellent sur les langues européennes
  occidentales) ou similaire pour produire un brouillon.
* **Validation** : relecture par un locuteur natif avant
  activation. Tant qu'une langue n'est pas relue, elle reste en
  « beta » (badge visible dans le sélecteur).
* **Contributions externes** : page `/about` mentionne « Vous parlez
  cette langue ? Aidez-nous à améliorer la traduction » avec lien
  vers le repo (issue ou PR sur le fichier YAML).
* **Sélecteur de langue** : drapeau + nom natif (« Deutsch »,
  « Italiano »…) plutôt que codes ISO. Persistance via cookie
  + `Accept-Language` HTTP en fallback initial.
* **Aucune langue activée tant que sa traduction n'est pas relue
  par un humain** — protège la qualité perçue (vitrine ALOLI).

=== B — Application desktop native (macOS / Linux / Windows)

🔵 — initiative stratégique. Effort estimé : **XL** (3-4 sem.
cumulées sur les trois OS, signature/notarisation incluse).

==== Cible

* Grand public qui n'ouvre pas de terminal.
* Workflows répétitifs (préparation hebdomadaire d'un livret
  liturgique : sélection multi-fichiers + clic droit dans le
  Finder/Explorateur).
* L'intégration au menu contextuel du gestionnaire de fichiers est
  **le cœur de la valeur** — c'est ce qui rend l'outil invisible et
  utilisable par n'importe qui.

==== Architecture

[cols="1,3"]
|===
| Layer | Tech

| Logique métier      | Le binaire `crystal-combine-pdf` lui-même, invoqué par l'UI via `Process.run`.
| UI macOS            | Native AppKit — réutilise `aloli-crystal/appkit` qu'on a déjà.
| UI Linux            | À étudier : GTK4 via FFI (natif, lourd) **ou** approche Tauri-like (UI HTML+JS dans une webview système, backend Crystal).
| UI Windows          | Tauri-like probablement le plus simple si on veut une UI partagée avec Linux.
| Service Finder/Explorer | Plate-forme spécifique (cf. tableau ci-dessous).
|===

==== Distribution

Décision Philippe (2026-05-03) : **publier dans les stores
plate-formes** en plus du téléchargement direct depuis
`alolipdf.app/download`. Pour atteindre le grand public, la
présence dans les stores est non négociable — c'est là que les
gens cherchent une « app PDF » par défaut.

[cols="1,2,4"]
|===
| OS | Store principal | Notes

| **macOS**
| Mac App Store
| Apple Developer Program à 99 USD/an. Sandbox obligatoire
  (entitlements `com.apple.security.files.user-selected.read-write`
  pour l'accès Finder). Notarisation Apple incluse. Process de
  review (typiquement 24-72 h). Direct download `.dmg` / Homebrew
  tap `aloli/tap` en parallèle pour les utilisateurs hors store.

| **Windows**
| Microsoft Store
| Microsoft Partner Center à 19 USD (one-shot pour individu) ou
  99 USD pour une société. Format **MSIX** (signature
  `App Identity` requise). Direct download MSI/portable `.zip` en
  parallèle.

| **Linux**
| **Flathub** (recommandé) + **Snap Store**
| Flathub gratuit, format Flatpak — couvre la majorité des distros
  modernes (Fedora, Ubuntu, Arch via Flathub installé). Snap Store
  gratuit, format Snap — cible Ubuntu en priorité. AppImage en
  parallèle pour le téléchargement direct (zéro store, zéro
  install). Packages `.deb`/`.rpm` natifs : nice-to-have, à
  prioriser selon la traction par distro.
|===

==== Implications de la contrainte « stores »

Présence en stores = sandboxing + revues + signatures, ce qui
impacte fortement la conception. À budgéter dès le départ :

* **Sandboxing macOS** : l'app ne peut accéder qu'aux fichiers
  explicitement sélectionnés par l'utilisateur. Heureusement, le
  cas d'usage « clic droit dans le Finder » entre exactement dans
  ce cadre via les entitlements `user-selected`.
* **Code signing** sur les 3 OS, dont notarisation Apple
  (automatique via `xcrun notarytool` en CI). Coût récurrent
  Developer Program inclus.
* **Process de review** initial (long, 1-2 sem.) puis chaque update
  (rapide ensuite, ~24-72 h). Préparer screenshots, descriptions
  i18n, captures vidéo de fonctionnement.
* **In-app purchase pour Pro** — sujet sensible :
  ** Apple App Store : règle du 30 % sur les transactions
     in-app. *Mais* DMA (UE, mars 2024) autorise les apps de l'UE
     à pointer vers un paiement web externe. Stratégie : compte
     Pro payé sur `alolipdf.app` + login dans l'app desktop, pas
     d'IAP. Hors UE, à arbitrer (peut nécessiter d'activer IAP).
  ** Microsoft Store : politique plus souple, IAP optionnel,
     paiement externe accepté.
  ** Flathub / Snap : aucune restriction de paiement.
* **Updates** : gérées par les stores quand on passe par eux, à
  monter soi-même pour les distributions directes (Sparkle pour
  macOS direct, WiX pour Windows MSI, etc.).
* **Effort total revu à la hausse** : XL → XXL (4-6 semaines
  cumulées), dont ~1/3 pour l'app elle-même et ~2/3 pour le tooling
  store/CI/signing.

==== Hors-périmètre v1

Édition page-par-page (zone graphique de tri/suppression), aperçu
PDF intégré, signature numérique.

== Ordre suggéré

1. **Optimisations** — déduplication ressources, `insert`/`remove`
   *(évolution naturelle ; donne un shard plus complet pour les
   apps dérivées)*.
2. **🔵 Application web v1** — la plus rapide à mettre debout, donne
   du retour utilisateur immédiat, sert immédiatement de vitrine
   ALOLI.
3. **Sécurité** — lecture/écriture de PDF chiffrés *(utile ISO 27001
   et pour les cas pro de la web app)*.
4. **🔵 Application desktop v1** — plus lourd, plus de plates-formes
   à valider, mais la valeur du clic-droit est unique.
5. **Signatures PAdES** *(long terme, dépend de l'évolution de
   `aloli-crystal/jose`)*.
